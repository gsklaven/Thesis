# Interpretation notes on the results (for Chapter 5)

The numbers, tables and lists are generated by `results/results_analysis.py` (`<tag>.md`,
`confusion_<tag>.svg/.tex`, `ablations.md`) and `results/thesis_tables.py` (LaTeX of the thesis). This file
holds the observations and interpretation, which the scripts do not rewrite.

## v12_sum - full system (samples + policies)

**Main results** (LLM stage, 416 malware / 130 benign packages with Behavior Chains)

- Recall 97.1% [95.0-98.3], FPR 6.2% [3.2-11.7], precision 98.1%, F1 97.6%, accuracy 96.3%,
  balanced accuracy 95.5%. End-to-end (including the packages without Behavior Chains): accuracy 95.6%.
- No `EVALUATION_FAILED` / `INCOMPLETE` evaluation: every package received a final verdict.
- The numbers come after all the cleaning steps: correct labels (without the legitimate MalwareBench
  packages), no shared code between index and test (family split), no analysis of library code (no vendoring).
- Not directly comparable with v11 (different test set, index and chains). For reference, v11 had recall 88%
  and FPR 27% (10/37).

**Generalisation to new malware** (strata of maximum similarity to the index)

- >=0.98 (known variant): recall 233/235 = 99.1%.
- 0.90-0.98 (close): recall 129/139 = 92.8%.
- <0.90 (novel, no close neighbour): recall **42/42 = 100%**. The system does not rely merely on similarity
  to known samples: the LLM recognises the behaviour from Section A.
- On benign packages, in contrast, the FPs concentrate in the high strata: 4/29 (>=0.98), 4/83 (0.90-0.98),
  0/18 (<0.90). The `llm` ablation (no retrieval) shows whether high similarity to malware pushes towards FP
  (it does - see below).

**False positives: one clear, recurring pattern**

- All 8 FPs have **exactly one** malicious Behavior Chain among many (e.g. psutil 1/94, oauth2client 1/70):
  a consequence of the "one `MALICIOUS` chain is enough" rule.
- 6 of the 8 are `setup.py` code that runs at installation:
  - 4 (frozendict, opencensus, fabric, opentelemetry-exporter-gcp-monitoring): the well-known legitimate
    version-reading pattern, `exec(open("<pkg>/version.py").read(), namespace)`.
  - crossplane: `os.system("{python} setup.py sdist bdist_wheel --universal")` (a release command).
  - daff: execution of a local `make` script during the build.
- The other 2: psutil (`tempfile.NamedTemporaryFile` in an internal pip-installation script), oauth2client
  (`pickle.loads` in a Django model).
- **Cause**: the Behavior Chain shows the read as `open(...)`, without the argument (file name), so the LLM
  cannot tell "exec of version.py" from "exec of a hidden payload" - and the similar flows in the index are
  indeed malicious (similarity 0.99-1.0). For fabric, the nearest neighbour (1.0) is `fabrice`, a
  typosquat of fabric that steals AWS credentials and contains a copy of fabric's `setup.py`.
- Possible improvement (future work): keep the constant arguments of the calls in the node texts (e.g.
  `open("pkg/version.py")`) - a change in `find_flow.ql`/`readableExpr` that needs a new CodeQL analysis.
  Not a prompt change: without the file name, a rule "exec in setup.py is harmless" would hide real malware.

**False negatives** (12): `@bigid-ui`, `celery-flower`, `celium-collateral-upgrade`, `dmclc`, `huzzleup`,
`juk`, `lium-4.96`, `pyphetools`, `rasterkit` (80 chains), `rblxtools`, `set-utils`, `set_utils`. 9 of them are
missed by all four configurations. Groups: (a) packages with extensive legitimate code whose evaluated chains
are the legitimate functionality (rasterkit - Pillow code, set_utils - web3 code, lium-4.96, celery-flower;
pyphetools runs its stealer from a `.pth` file); (b) one or two actions of ordinary form (huzzleup - HTTP GET
to httpbin at install time, juk, celium-collateral-upgrade, dmclc, @bigid-ui, rblxtools); (c) the ambiguous
`exec` pattern in `setup.py` (set-utils). Static misses (no chain): 6 malware (1.4%).

**Statistical power**

- The FPR rests on 130 benign packages with chains, hence the wide confidence interval (3.2-11.7%). Extra:
  an evaluation on the ~3,200 legitimate packages that MalwareBench had labelled as malware by mistake
  ("hard" benign packages) would stabilise the FPR estimate.
- The classes are imbalanced (416 vs 130): accuracy is reported together with balanced accuracy / F1.

**Execution**: ~2.5 hours with malware and benign in parallel (two terminals), 8 parallel calls per package.

## Ablations (samples / policy / llm)

Summary table: `ablations.md`. The comparison uses the same packages and the same index, so only the
content of Sections B/C of the prompt differs.

### v12_samples - malware samples only (no security knowledge base)

- Recall 96.6% [94.4-98.0], FPR **3.1%** [1.2-7.6], precision 99.0%, F1 97.8%, accuracy 96.7%, balanced
  accuracy 96.8%, end-to-end accuracy 95.9%. Every package received a final verdict.
- Compared with `sum`: FP 8 → 4, FN 12 → 14. Per package:
  - benign packages that stopped being FP (5): oauth2client, crossplane, opentelemetry-exporter-gcp-monitoring,
    frozendict, opencensus; new FP (1): qtconsole (`exec` in `setup.py`); shared FPs (3): psutil, daff, fabric.
  - malware lost (4): ansiicolor, moneyprinter-api, pohttp, ttensorflow-gpu; malware detected only here (2):
    rblxtools, set-utils.
  - McNemar (exact): benign 5 vs 1, p = 0.22; malware 4 vs 2, p = 0.69. The two configurations are
    statistically equivalent overall; they differ in the operating point (sensitivity vs FPR).
- **Role of the security knowledge base: it raises sensitivity.** When Section C contains a rule that names
  the behaviour, the LLM uses it to support the suspicious reading. Examples (same Behavior Chain, same
  neighbours in Section B):
  - moneyprinter-api, ttensorflow-gpu: execution of a local script / `subprocess.Popen` in `setup.py`. With the
    Semgrep `dangerous-os-exec` / `subprocess-injection` rules: MALICIOUS; without: "standard setup.py
    functionality". ttensorflow-gpu is detected only by the two configurations that include Section C.
  - frozendict (benign): `exec` of the version file in `setup.py`. With Bandit B102 (`exec`) and Semgrep
    `exec-injection`: MALICIOUS; without: "standard build-time metadata/version extraction", BENIGN.
  - pohttp (base64 → `__import__` in `setup.py`) and ansiicolor (a test that downloads a binary from Dropbox and
    runs it) are detected by `sum`, `policy` and `llm`; only with sample retrieval alone does the LLM accept a
    harmless explanation ("setup scripts commonly … use base64", "string literal used in tests").
- **The `exec(open(...).read())` pattern in `setup.py` is ambiguous at the Behavior Chain level.** set-utils
  (malware) uses exactly the same pattern to execute its own file at install time as the legitimate
  frozendict/opencensus use for their version file. Verdicts on these packages change between
  configurations, confirming that the distinction needs the content or at least the name of the executed file
  (see future work above).
- Similarity strata: >=0.98 recall 232/235, FP 2/29; 0.90-0.98 recall 128/139, FP 2/83; <0.90 recall
  **42/42**, FP 0/18. Without policies too, novel malware (no close neighbour) is fully detected.

### v12_policy - security knowledge base only (no samples)

- Recall 96.2% [93.8-97.6], FPR 4.6% [2.1-9.7], precision 98.5%, F1 97.3%, accuracy 96.0%, balanced
  accuracy 95.8%, end-to-end accuracy 95.3%. Every package received a final verdict.
- Validity checks: Section B is empty ("No similar malware found") in all 16,488 Behavior Chains; file paths in
  the prompt are package-relative in both classes (`setup.py`, `azure/__init__.py`), with no trace of the
  sample's source; the words "malware"/"malicious" appear only through the prompt template, equally in both
  classes.
- Compared with `sum`: malware 5 lost / 1 gained (McNemar p = 0.22); benign 4 FPs fixed / 2 new (p = 0.69).
  Statistically equivalent.
- FP (6): google-auth, opencensus, fabric, furl, opentelemetry-exporter-gcp-monitoring (all `exec` in
  `setup.py`) and daff (`Subprocess.call`). 5 of the 6 are the version-file `exec` pattern, with the retrieved
  Bandit B102 / Semgrep `exec-injection` rules: the `exec` rules push towards MALICIOUS even without samples.
- FN (16): @bigid-ui, celery-flower, celium-collateral-upgrade, colorfades, dmclc, easy-https, huzzleup,
  lightmock, lium-4.96, pantheon-agents, pyphetools, rasterkit, rblxtools, reuquests, set-utils, set_utils.
- Similarity strata (from `sum`): >=0.98 recall 228/235, FP 4/29; 0.90-0.98 recall 130/139, FP 2/83; <0.90
  recall 42/42, FP 0/18. Known variants are detected even though the LLM does not see the similar samples.

Observations:
- On benign packages the LLM checks the retrieved policies one by one against the code and rejects those that
  match only the name of the call (e.g. "Matches the API, but the data written is test attachment content").
  Without Section B there is no malware neighbour with specific tags, so the decision rests on Section A alone.
- fabric (`exec` in `setup.py`, with Bandit B102 / Semgrep `exec-injection`) and daff are FPs as in `sum`: the
  `exec`/`subprocess` rules push towards MALICIOUS without samples too. In daff the chain is
  `Subprocess.call` in `__init__.py` and the reasoning talks about possible command injection - here the LLM
  confuses the vulnerability described by the Semgrep rule with malicious intent.

### v12_llm - no retrieval

- Recall 96.2% [93.8-97.6], FPR **0.8%** [0.1-4.2], precision 99.8%, F1 97.9%, accuracy 96.9%, balanced
  accuracy 97.7%, end-to-end accuracy 96.1%. Every package received a final verdict.
- FP (1): psutil (`shutil.rmtree` in `scripts/internal/purge_installation.py`).
- FN (16): @bigid-ui, celery-flower, celium-collateral-upgrade, dmclc, huzzleup, juk, lium-4.96,
  pantheon-agents, pxhttp, pyphetools, pyshftuler, rasterkit, set-utils, set_utils, solana-web3-alt,
  ttensorflow-gpu.
- The FPs of the retrieval configurations that involve `exec`/`subprocess` in `setup.py` (fabric, frozendict,
  opencensus, daff etc.) are BENIGN here with confidence 0.90-0.95 ("ordinary setup.py functionality such as
  reading a requirements file, version file…").
- Similarity strata (from `sum`): >=0.98 recall 231/235, FP 0/29; 0.90-0.98 recall 127/139, FP 1/83; <0.90
  recall 42/42, FP 0/18.

## Synthesis of the ablations: what retrieval contributes

| | `sum` | `samples` | `policy` | `llm` |
|---|---|---|---|---|
| Recall | **97.1%** (404) | 96.6% (402) | 96.2% (400) | 96.2% (400) |
| FPR | 6.2% (8) | 3.1% (4) | 4.6% (6) | **0.8%** (1) |
| F1 | 97.6% | 97.8% | 97.3% | **97.9%** |
| Balanced accuracy | 95.5% | 96.8% | 95.8% | **97.7%** |
| TP with SSVC `ACT` | **343** | 339 | 301 | 313 |
| FP with SSVC `ACT` | 1 | 1 | 0 | 1 |

**1. The Behavior Chain carries the main signal.** 392 of the 416 malware packages are detected by all four
configurations, 9 by none; 119 of the 130 benign packages are correct in all four, none is an FP in all of
them. The configurations differ on 15 malware and 11 benign packages. In the "novel" stratum (<0.90) recall is
42/42 in every configuration.

**2. Retrieval detects malware hidden inside legitimate code.** Detected by every configuration with
retrieval, not without it:
- pyshftuler (152 chains, a copy of `requests`): base64 → `compile` → `exec` in `models.py`. Without retrieval
  the LLM attributes it to "documented functionality of the requests library" (BENIGN, 0.95); with retrieval it
  finds the same code in the index (similarity 1.0) and a neighbour tagged `data_exfiltration`.
- pxhttp: base64 → `__import__` in `setup.py`. Without retrieval: "common legitimate setup.py patterns" (0.7).
- solana-web3-alt: `setup.py` runs a hidden `trigger.py`. With retrieval the neighbour pylogfmt (0.92, tags
  `supply_chain_downloader`, `spyware_infostealer`) describes exactly the same pattern.
- Also pantheon-agents (reading of Gemini CLI credentials, neighbour tagged `credential_stealer`, caught by
  `sum` and `samples`) and ttensorflow-gpu (caught by `sum` and `policy`).
In these cases the LLM on its own rationalises the behaviour through the package's legitimate functionality;
the retrieved sample with specific tags overturns that rationalisation.

**3. Retrieval makes detections of real malware more decisive.** With the full system, 343/404 TPs (85%) get
the highest SSVC decision `ACT`, against 313/400 (78%) without retrieval, with the same number of FPs at `ACT`
(1). The other FPs of `sum` are `ATTEND` (analyst review), not an automatic response.

**4. Retrieval pushes ambiguous installation patterns towards MALICIOUS.** The FPs of the retrieval
configurations that are absent from `llm` concern 10 benign packages: 9 involve `exec` or subprocesses, mostly
in `setup.py`, and the tenth (oauth2client) `pickle` deserialisation. The malware neighbours have the same code
shape and the rules name the same API. `sum` vs `llm` on benign packages: 0 vs 7, McNemar p = 0.016 - the only
statistically significant difference between the configurations.

**5. Evidence.** In `sum` every MALICIOUS verdict (412/412) comes with the most similar known malware and with
specific security entries (ATT&CK/CWE/CAPEC/Bandit/GuardDog/Semgrep); in `llm` none does.

**Statistics (McNemar, vs `llm`)**: `sum` malware 5/1 p = 0.22, benign 0/7 p = 0.016, overall 5/8 p = 0.58;
`samples` overall 5/6 p = 1.0; `policy` overall 6/11 p = 0.33. In overall accuracy the four configurations are
equivalent; they differ in the kind of errors and in decisiveness.

**Relation to the literature**: in IntelGuard's own ablation, direct LLM analysis (GPT-4o-mini) already reaches
96.99% accuracy on PyPI vs 99.00% with retrieved knowledge; the large gain appears on obfuscated code (52.82% →
96.50%).

**Conclusion for Chapter 5**: retrieval works as a sensitivity regulator - it detects malware that imitates
legitimate code and makes verdicts more decisive and better documented, at the cost of more review alarms on
ambiguous installation patterns. Improvement for future work: constant arguments in the Behavior Chains (e.g.
`open("pkg/version.py")`), so that neighbours and rules do not match on the shape of the call alone.
